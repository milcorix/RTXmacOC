# MilcorixFB на маке — рабочий цикл

Документ отвечает на один вопрос: **что нажимать, чтобы двигаться вперёд и не
остаться без картинки.** Он написан после того, как драйвер один раз превратил
машину в кирпич — все решения ниже приняты, чтобы это не повторилось.

---

## Почему раньше ломалось (одной фразой)

Слой 5 кладёт фреймбуфер во **VRAM**, а kext отдавал этот же адрес системе как
**физический адрес обычной памяти**. WindowServer писал рабочий стол в чужую
RAM: картинки нет, а заодно тихо портится память — так был убит dyld-кэш и
получена петля перезагрузок с `Bad CPU type in executable`. Подробности и
источники — `docs/gsp-layer5-display.md` и память проекта.

---

## Три предохранителя, которые теперь есть

1. **По умолчанию драйвер выключен.** Он читает boot-arg `milcorix=N`; без него
   не подключается вообще. Установка kext'а сама по себе ничего не меняет.
2. **Драйвер подключается только с годной апертурой.** Железо поднимается ДО
   `super::start()`, и фреймбуфером системы мы становимся, лишь получив
   CPU-писабельный буфер. Любой сбой → не подключаемся → macOS рисует через
   EFI-фреймбуфер, рабочий стол на месте.
3. **Журнал переживает чёрный экран.** Трейс загрузки пишется в файл на диск, а
   однострочный итог — в NVRAM. И то и другое читается **из Linux**, даже если
   macOS вообще не догрузилась. Фотографировать экран больше не нужно.

---

## Стадии

| `milcorix=` | Что делает | Чем рискуем |
|---|---|---|
| `0` (дефолт) | ничего, kext не подключается | ничем |
| `1` | поднять GSP (слои 2–4), **вывод не трогать** | ничем: картинка остаётся EFI-шной |
| `2` | + modeset и наш фреймбуфер | картинка может не появиться → стадия 0 и разбор журнала |

Дополнительно `milcorixfb=` выбирает, откуда берётся буфер:
`0` авто (по умолчанию), `1` только VRAM через BAR1, `2` только системная память.

Переключение — **из Linux, одной командой**:

```sh
sudo python3 tools/milcorix_stage.py 1      # поставить стадию
sudo python3 tools/milcorix_stage.py        # показать итог прошлой загрузки
```

## Порядок работ

### Шаг 1. Убрать со стенда СТАРЫЙ kext

Старый бандл подключался всегда и про boot-arg'и не знал — его надо снести, а не
чинить поверх.

Если macOS **загружается**: открой терминал и переходи к шагу 2 (скрипт удаления
там же). Если **не загружается** — сначала Recovery:

```
diskutil mount disk2s1                       # EFI (номер смотри в diskutil list)
sh /Volumes/*/milcorix-recovery.sh           # отключает AuxKC + собирает логи
```

затем перезагрузка в обычный macOS.

### Шаг 2. Взять свежий код на маке

Репозиторий CI публичный, Xcode на маке есть:

```sh
cd ~/Downloads
git clone https://github.com/BandUSER227/RTXmacOC-ci.git RTXmacOC-new
cd RTXmacOC-new
sudo tools/macos_uninstall.sh                # вычистить старое
```

### Шаг 3. Собрать и поставить

```sh
sudo tools/macos_install.sh ~/Downloads/milcorix-fw
```

(последний аргумент — каталог с прошивками; если они уже разложены, его можно не
указывать). После установки драйвер **выключен** — это норма.

### Шаг 4. Стадия 1 — убедиться, что драйвер живой и безвредный

Из Linux:

```sh
sudo python3 tools/milcorix_stage.py 1
```

Перезагрузиться в macOS. Ожидание: **обычный рабочий стол** (вывод не трогали).
Затем обратно в Linux и посмотреть, что получилось:

```sh
sudo python3 tools/milcorix_stage.py         # строка итога из NVRAM
sudo apfs-fuse /dev/nvme0n1p3 /mnt/mac       # если нужен полный журнал
less "/mnt/mac/root/Library/Application Support/Milcorix/lastboot.log"
```

Хороший итог: `ok:bringup-only`, а в журнале — цепочка до `GSP_INIT_DONE` и
перечисление дисплеев.

**На этой же стадии проверяется слой 6.** Драйвер заставляет видеокарту
выполнить нашу собственную команду — копирование 64 КиБ движком CE — и сверяет
результат побайтно. Вывод при этом не трогается вообще, так что рисковать
картинкой не нужно. В NVRAM попадёт `gpu:copy-ok`, а в журнале:

```
СЛОЙ 4: контекст исполнения отдан платформе — канал=0x... CE=0x... token=0x...
СЛОЙ 4 B: classEngineID ... id=0x...
*** СЛОЙ 6: GPU ИСПОЛНИЛ НАШУ КОМАНДУ ПОД macOS — копия 64 КиБ движком CE сошлась побайтно ***
```

Это фундамент вычислительного применения карты: тот же канал и тот же механизм
отправки дальше несут любую нашу работу.

### Шаг 5. Стадия 2 — вывод через нашу карту

```sh
sudo python3 tools/milcorix_stage.py 2
```

Перезагрузиться. Два исхода:

- **Картинка есть** — слой 5 замкнут на macOS.
- **Картинки нет** — вернуться в Linux, `milcorix_stage.py 0`, и прочитать
  журнал: там будет видно, подтвердилось ли identity-окно BAR1, какой буфер
  выбран, прошёл ли modeset и какая апертура опубликована.

**Одношаговая проверка апертуры.** В boot-args уже есть `-v`. С ним ядро само
заливает нашу апертуру серым (`0xbfbfbf`) и рисует яблоко ещё до WindowServer.
Значит: **если в момент подхвата фреймбуфера экран не изменился — апертура
неверна**, и дальше можно не гадать. Если нужен громкий вариант, добавь
`iog=0x80` — тогда тихий отказ апертуры превращается в панику с причиной.

Ключевые строки, которые стоит искать в журнале:

```
консоль EFI @phys=0x... = BAR1+0x...          ← где UEFI оставил буфер
BAR1 identity ПОДТВЕРЖДЁН / НЕ подтверждён
scanout-FB во VRAM@... через BAR1  |  scanout-FB в СИСТЕМНОЙ памяти
СЛОЙ 5 C.4e-ф2: core SOR+modeset ... GET==PUT
SOR ... ARM=... OR АКТИВЕН
head0 vline ... СКАНИРУЕТ
gspBringUp OK — ... CPU-апертура phys=0x...
MilcorixFB[trace] isConsoleDevice -> 1          ← система спросила про консоль
MilcorixFB[trace] getApertureRange(0)           ← система забрала буфер кадра
MilcorixFB[trace] WindowServer подключился      ← композитор дошёл до нас
```

Последние три — самые важные. Если их нет, значит система с нами **не
разговаривает** (проблема в матчинге/категории), а не в железе. Если они есть, а
картинки нет — проблема в адресе апертуры или в modeset.

---

## Если картинки нет на стадии 2

Порядок разбора, от дешёвого к дорогому:

1. `milcorixfb=2` — заставить взять буфер в системной памяти (обходит BAR1
   целиком). Если так картинка появляется — вопрос в identity-окне BAR1.
2. `milcorixfb=1` — наоборот, только BAR1. Если journal говорит «identity НЕ
   подтверждён», значит после инициализации GSP-RM прошивка перестроила таблицы
   BAR1, и нужен свой маппинг под `bar1PdeBase` (адрес приходит в
   `GET_GSP_STATIC_INFO`, PTE пишутся нашим же GMMU-кодом).
3. Если modeset проходит (`GET==PUT`, `OR АКТИВЕН`, `СКАНИРУЕТ`), а картинки
   нет — дело не в железе, а в том, принял ли WindowServer нашу апертуру.

---

## Аварийный откат (всегда работает)

Из Linux:

```sh
sudo python3 tools/milcorix_stage.py 0
```

Драйвер не подключится, macOS загрузится через EFI-фреймбуфер. Полное удаление —
`sudo tools/macos_uninstall.sh` уже на маке.
